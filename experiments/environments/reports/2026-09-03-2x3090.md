# Native environment validation on two RTX 3090 cards

## Verdict

Both **native environments and two-rank CUDA/NCCL canaries are installed and
working**. SimCT's dependency check is clean. X-Token has five explicitly
excluded upstream CUDA 13/transport requirements; its dependency check is
therefore nonzero. **X-Token attempt 5 now passes three real optimizer updates**
after a diagnosed, opt-in NCCL host-memory workaround. All recorded training
scalars are finite; both GPUs were used. SimCT remains environment/canary
evidence only: no SimCT training has run.

This is a short off-policy engineering smoke, not OPD, an X-Token/SimCT paper
reproduction, model-quality evidence or a 1-GPU/2-GPU scaling comparison.
Previous failed attempts remain in the evidence history. No dependencies,
model precision, loss, dataset, optimizer or upstream algorithm code were
changed to resolve the CUDA failure.

The prior machine's setup was not entirely lost: source pins, harness and
earlier unit-test evidence survived. The native overrides/lockfiles were not
previously published. This directory now packages both complete dependency
resolutions instead of relying on a rented machine's mutable venv.

## Diagnoses and continuation gate

1. Missing `+` on newly added Hydra `automodel_kwargs` keys caused launch 1 to
   stop during config parsing (8.661 s). Fixed; config-only validation passed.
2. Choosing the independent uv project as **cwd** caused launch 2 to fail
   loading the upstream relative prompt `examples/prompts/cot.txt` (15.442 s).
   Fixed by setting **NeMo source cwd** and explicit `uv --project <native-env>`.
   Config/tokenizer/data validation now passes without Ray or a training run.

Neither initial launcher failure demonstrates TPU/GPU OOM, bad distillation
math or unsuitable 3090 hardware. Neither produced an optimizer update.

3. User-approved attempt 3 ran the unchanged published code
   `d04f0147171fd9a152942ef720db36c3cc162807`, after a fresh matching config gate.
   Qwen3 teacher initialization reached both Ray workers. During setup,
   `teacher_policy.offload_after_refit()` called `move_to_cpu()` and
   `move_buffer_to_device()`; rank 1 reported a CUDA illegal address at
   `torch.utils.swap_tensors(v, v.to(device))`. Both ranks' NCCL watchdogs then
   aborted. This is before the training loop, so **zero optimizer updates**.
   CUDA is asynchronous: this stack identifies where the error surfaced,
   not necessarily the kernel that originally caused it. Hardware failure,
   OOM, P2P/NCCL incompatibility and a specific package defect are not proven.
   A generic Ray warning listing OOM as one possible cause is not an OOM proof.

Attempt 3 exited 1 in 37.013 s without hitting its 1200 s timeout. There were
three 15-second telemetry samples; the largest sampled memory was 284 MiB per
GPU (not a measured peak). After cleanup, both GPUs returned to 1 MiB/0% with
no training/Ray workers left. Attempt 3 logs, command, result, telemetry, marker
and TensorBoard files have been copied off-host. The user subsequently
authorized continuing deployment and CUDA debugging; the controlled probes
below and distinct attempt 5 followed that authorization.

| `083832.083218Z-cuda-probe-ray-cumem-host0-f74e6d2a` | **exit 0, 43.372 s** | Only `NCCL_CUMEM_HOST_ENABLE=0`: both Ray ranks initialize, read finite buffers and offload successfully |

These probes used synchronous CUDA diagnostics and never trained or saved
checkpoints. Each invocation had its own exclusive marker and 240-second
timeout. Probe-code defects are separated above from the workload defect;
there was no unchanged automatic retry. Earlier probe markers predate adding
NCCL settings to marker metadata; their transport variants are documented by
the executed command record and diagnostic logs, not a backfilled claim about
those original JSON files.

The error and effective workaround match
[NVIDIA NCCL issue 1838](https://github.com/NVIDIA/nccl/issues/1838), concerning
cuMem host-memory sharing on devices without peer access. The supported local
diagnosis is an NCCL cuMem host-sharing incompatibility under this host's
Ray-isolated device visibility. It is not proof of broken GPUs, insufficient
disk/RAM, OOM or incorrect distillation math. The same thread IDs were observed
at Ray construction and the later method, so thread migration was not supported
as the cause.

The only operational workaround in trainer attempt 5 was
`NCCL_CUMEM_HOST_ENABLE=0`; no `NCCL_P2P_DISABLE` or `CUDA_LAUNCH_BLOCKING`
was set for that training run. The installed NCCL package is **2.28.9** under
Torch **2.11.0+cu128**. The inherited image label `NCCL_VERSION=2.25.1-1`
is also recorded but must not be mistaken for the installed Python package.
The opt-in launcher flag, all inherited NCCL/allocator debug settings and
2-GiB minimum launch disk check are recorded in the config/attempt gate.
It changes host allocation behavior, not precision or scientific configuration.
